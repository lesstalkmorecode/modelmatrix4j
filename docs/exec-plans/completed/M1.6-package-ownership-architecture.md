### Reconciled package architecture

No package below is created or pre-authorized by M1.6. Each path becomes valid only with its first approved concrete current-milestone type.

| Module/package | Disposition | Cohesive responsibility |
| --- | --- | --- |
| `com.modelmatrix4j.core.scenario` | Conditional M2 public package | Provider-neutral scenario identity and minimal scenario input. |
| `com.modelmatrix4j.core.model` | Conditional M2 public package | Immutable model identity/descriptor and non-secret descriptive metadata only. The name is accepted because it maps to the documented model-descriptor responsibility, not a generic domain bucket. |
| `com.modelmatrix4j.core.execution` | Conditional M2 public package | Smallest executable model-under-test boundary and programmatic execution surface required by consumers. |
| `com.modelmatrix4j.core.result` | Conditional M2 public package | Immutable run facts, terminal status, safe diagnostics, and minimal M2 compatibility result. |
| `com.modelmatrix4j.core.compatibility` | Rejected for M2 | One minimal aggregate does not justify a package; reconsider only with demonstrated later growth. |
| `com.modelmatrix4j.core` | Existing namespace, not a bucket | No miscellaneous types; use only for a proven top-level entry point if later justified. |
| `com.modelmatrix4j.core.internal...` | Conditional implementation-only families | Responsibility-named orchestration, comparison, or diagnostic packages only when several concrete collaborators justify separation. No flat dumping ground. |
| `com.modelmatrix4j.junit` | Conditional M2 public package | Minimal test-author annotation, facade, or supported extension entry point. |
| `com.modelmatrix4j.junit.api` | Rejected | Exposure is not an architectural responsibility and duplicates the public root. |
| `com.modelmatrix4j.junit.internal...` | Conditional implementation-only families | Lifecycle/resolution mechanics; descendant split deferred until concrete classes prove independent cohesion and direction. |

Dependency direction is foundational `scenario` and `model`, then `result` may reference their identities, then `execution` may consume all three. Exposed signatures never contain internal types. A narrowly reviewed public entry point may invoke internal implementation only when no dependency path returns from that implementation to the calling entry-point package. An entry point inside `execution` therefore cannot call a helper depending back on `execution`; a separately located composition entry point may call internal orchestration consuming supported execution contracts when no dependency returns to composition. Other core internals consume public contracts; comparison/diagnostics do not depend back on orchestration. JUnit depends only on supported core public packages, never core internals; core never depends on JUnit.

### Reconciled ownership model

- Ownership is a temporary task lease, not permanent authority attached to an agent, role, or package.
- Prefer exact files. A bounded path must state recursion and exclusions; broad module roots are prohibited when a narrower scope is knowable.
- A public/protected signature or cross-package dependency change is a shared-contract event: stop, escalate, revise scope, update the API inventory, sequence affected owners, and obtain independent API review.
- No file is shared writable. Overlap—including broad/narrow path overlap—forces sequential work after handoff reconciliation and explicit release.
- A cohesive atomic change may receive an exact cross-package file set when splitting would invent an unstable intermediate API; otherwise sequence inward-to-outward contracts and implementations.
- Production plus directly corresponding tests may share one bounded task. A separate test owner is read-only over production and starts after production reconciliation.
- Conditional examples: scenario contract owner → named `core/scenario` files/tests; model descriptor owner → named `core/model` files/tests; result owner → named `core/result` files/tests; execution owner → named `core/execution` files/tests; comparison mechanics owner → named `core/internal/comparison` files/tests after result; JUnit public owner → exact module-root public files/tests; JUnit mechanics owner → named `junit/internal` responsibility files/tests after public contracts.

### Reconciliation decisions and risks

- D1's four core responsibilities are accepted, but every package is conditional. D4's objection that `model` could become generic is addressed by restricting it to documented descriptor identity/metadata and prohibiting unrelated domain types.
- Compatibility is merged into `result` for M2; D1 and D4 agree that a separate package would be premature and invite M7 concerns.
- D3's root-only preference is not adopted for core because four concrete responsibilities provide useful dependency and ownership seams. Its minimal-exposure and non-leakage rules apply to every retained public package.
- `junit.api`, automatic `spi`/`domain` layers, flat `internal`, lifecycle/resolution descendants, generic technical packages, test-support packages, and future capability packages are rejected or deferred.
- `.internal` does not enforce encapsulation. Independent API review must inspect the entire exposed type graph, including generic bounds, exceptions, annotations, inheritance, records, sealed permits, and public constants.
- No ArchUnit, JPMS, package-info placeholder, or other tooling is justified before concrete code demonstrates a stable executable rule.
