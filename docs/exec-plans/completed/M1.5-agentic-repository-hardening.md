## Reconciled findings

### Repository and documentation

- The current two-module reactor is the intended M1 shape. Core and JUnit responsibilities and inward dependency direction are coherent.
- The repository is appropriately sparse: it has no production Java classes, empty production packages, placeholder APIs, premature adapter modules, or shared test-support module.
- Governing documents, ADRs, and execution plans already have distinct roles. A new template or execution-plan README would duplicate workflow rules and is not justified at current scale.
- The Java namespace is implicit: existing tests use `com.modelmatrix4j`, while Maven coordinates use `io.github.lesstalkmorecode`. M2 must not leave this choice to individual implementers.

### Agentic workflow

- The workflow defines delegation contracts, exclusive ownership, dependency sequencing, and independent review, but the ledger alone cannot prove actual delegation or independence.
- Agent/delegation identity, task status meanings, contract evidence, handoff evidence, reconciliation decisions, and ownership release are not yet recorded consistently.
- A returned handoff is not the same as a reconciled dependency. Dependent work must remain blocked until the orchestrator records reconciliation.
- The completed M1 plan predates the multi-agent workflow and must not be retrofitted with invented delegation evidence.

### Package and public API discipline

- M2 needs a convention, not a speculative package map. Public surface should remain small and module-centered.
- Passing compilation cannot prove that a public abstraction has a real use case. Public API minimality requires an inventory and independent review.
- Test fakes belong in test source in the module whose contract they exercise. A shared test-support module remains deferred until actual duplication proves a need.

### Quality gates

- Existing Java-version, convergence, known core dependency-ban, test-lifecycle, and CI-command gates remain useful executable evidence.
- Current checks do not fully prove that core has no production JUnit or other arbitrary compile dependencies, that JUnit contains no later-milestone dependencies, or that tests avoid network/global nondeterminism.
- `GATE-M2-03` conflates behavioral mismatch with execution failure classification; the domain and test strategy distinguish them.
- M2 redaction, bounded diagnostics, public-API discipline, deterministic isolation, and milestone-specific dependency scope need explicit deferred gates before M2 begins.
- Agent authenticity, architectural intent, package cohesion, API necessity, exact milestone scope, and reconciliation truth remain manual judgments. Automating their document shape would provide false assurance.

## Proposed repository and package conventions

1. The Java package root is `com.modelmatrix4j`, matching the existing source packages. Maven group coordinates do not determine Java package names.
2. `com.modelmatrix4j.core` is the sole candidate public package for the minimal core API; `com.modelmatrix4j.core.internal` contains non-public orchestration and normalization mechanics.
3. `com.modelmatrix4j.junit` is the sole candidate public JUnit-facing package; `com.modelmatrix4j.junit.internal` contains non-public extension lifecycle and resolution mechanics.
4. Create a package only when its first approved concrete class is implemented. Do not create empty directories, package-info placeholders, or reserved subpackages.
5. Do not pre-split the small API into `api`, `spi`, `domain`, `model`, `service`, `runner`, `assertion`, or `util` packages. Add a narrower package only after several concrete cohesive classes demonstrate the need.
6. Production tests mirror the package under test. Consumer-facing API tests should use a package that cannot access internals when that separation is material.
7. Deterministic fakes remain test-scoped and local to the consuming module. No shared test-support module is created in M1.5 or speculatively for M2.

These are conventions for future authorized implementation. M1.5 creates no Java directories or classes.

## Public versus internal API rules

- Default every new type, constructor, and member to the narrowest visibility. Public visibility requires a named current-milestone use case and a consuming test.
- Maintain a public-API inventory in the active milestone plan mapping each public type or member to its use case and test evidence.
- Public signatures may reference only JDK types and intentional public types from allowed inward modules. They must not expose `.internal` types, framework/provider types, executors, clocks, mutable lifecycle state, or later capability projections.
- Core must not expose JUnit types. JUnit may expose the smallest test-author facade while keeping discovery, parameter resolution, invocation state, and failure mapping internal.
- Concrete immutable values are preferred over interfaces. Do not add builders, registries, generic events, lifecycle objects, or provider abstractions without a demonstrated consumer.
- Package placement does not by itself make an API stable; the independent API review and inventory are authoritative.

## Agent ownership rules

- Every task records a stable task ID, actual agent/delegation identity, exact writable scope, dependencies, status, contract, handoff, and reconciliation evidence in the active plan.
- Writable ownership is exclusive. Overlapping paths require sequential tasks; ownership is released only after the prior handoff is reconciled.
- Newly discovered files remain forbidden until the orchestrator revises the delegation and ledger.
- The implementer and each independent reviewer must have different actual agent/delegation identities. Role labels alone do not prove independence.
- The orchestrator inspects the integrated diff, disposes every finding, and records final verification; agent success reports are not completion evidence.

## Task dependency rules

- Dependencies reference stable task IDs and must be acyclic.
- A task may be delegated or started only after every listed dependency is `Completed` and its handoff reconciled, not merely returned.
- Architecture and test planning may run in parallel.
- Implementation begins only after its required planning dependencies are reconciled.
- Review and adversarial review begin only after the implementation they inspect is complete and its writable ownership has been returned.
- Independent reviews may run in parallel with each other.
- Tasks without a dependency relationship may run in parallel only when writable scopes do not overlap.
- Corrective implementation depends on reconciliation of the findings it addresses; final verification depends on all corrections and finding dispositions.

## Review and handoff requirements

- Each delegation contract records objective, allowed files, forbidden files, acceptance criteria, dependencies, and expected evidence in a named plan section or unambiguous ledger reference.
- A writing handoff records actual agent identity, changed files, commands and results, assumptions, limitations, and remaining risks.
- A read-only handoff records evidence inspected, findings with locations and severity, limitations, and recommendation.
- Reconciliation records accepted, rejected, or deferred recommendations with reasons; finding dispositions; scope or ownership changes; and the evidence that unlocks dependent tasks.
- Statuses have distinct meanings: `Planned`, `Delegated`, `In progress`, `Handoff returned`, `Reconciled`, `Completed`, and `Blocked`. `Completed` requires reconciliation; writable ownership is released at `Reconciled`.
- Final verification records the command, environment/JDK, reconciled workspace identity, result, and confirmation that it ran after all accepted edits.

Resolution: correct the documentation/manual gate now; defer any POM enforcement change to separately authorized work based on the exact dependency rule.
- **Deferred M2 gates:** deferral is correct before implementation, but missing gate definitions and ambiguous mismatch semantics could steer generated code incorrectly. Resolution: clarify and expand the deferred mapping without marking any M2 gate passed.

- Over-detailed package rules could become architecture by taxonomy. The convention therefore stops at public module roots and one internal subtree.
